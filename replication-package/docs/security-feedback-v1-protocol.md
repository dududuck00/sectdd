# Incremental contribution of security-test feedback

## Question and design
Does adding visible security-test feedback to functional-test feedback improve hidden functional-and-security joint correctness at the same revision budget?

Use every task from the existing 20-task balanced grid (8 CWEval, 8 SALLM, 4 CodeGuard+), Qwen2.5-Coder 7B/14B, five seeds (151001, 151021, 151051, 151057, 151091). Reuse the same 200 archived B0 initial responses and their visible observations used in the fixed-call study. Each initial enters two newly generated branches: functional_only and functional_security. Both make exactly two revision calls, even when visible tests pass. Total: 400 new trajectories, 800 new calls, no fresh initial generation. All tasks were previously observed; this is a post-primary mechanism experiment, not a fresh generalization set.

## Intervention
Both branches receive the original prompt/code history and the same revision instruction. Feedback has independent functional and security channels. Each channel reports PASS/FAIL for that channel only, then at most two failed cases in fixed identifier order, with case identifier, type, property description and the last twelve failure lines. Each channel is capped at 280 tokenizer tokens. The common revision instruction plus channels must fit the 600-token total feedback ceiling.

The functional_only branch receives only the functional channel. It receives no security status, security-case list, security failure, or full-suite aggregate status. Its functional message is invariant to changes in security observations at the same candidate state. The functional_security branch receives this same functional channel followed by a separately capped security channel. Security details cannot displace or truncate functional details. After the first revision, candidate states can diverge; identical functionality messages are guaranteed at the shared initial state, not across different subsequent states.

This tests availability of security execution information conditional on a fixed functional-feedback policy. It is not a new version of M, and it is not a token-matched comparison to neutral extra text. Realized token use differs by design; the maximum calls, completion tokens, context, functional information channel, and original requirements are controlled. Public requirements may already state security constraints in both arms. Functional failures can naturally mention security-relevant APIs; the intervention withholds security-test observations, not all security-related language.

## Execution
BF16 local checkpoints; temperature 0.2; 3072 output tokens per revision; 32768 context; same seed + revision index in both branches. Preserve every response before evaluating it; resume persisted responses after infrastructure interruption without resampling. Freeze both branches' messages using only visible execution. Evaluate hidden outcomes only after the final revision; use the existing isolated oracles. Check infrastructure failures separately and never treat sandbox startup errors as model failures. Syntax errors, import errors caused by candidate code, and actual candidate timeouts remain outcomes. The complete 400-cell grid is required before inferential reporting. A deterministic shuffle schedules the balanced grid; it is not randomized treatment assignment.

## Frozen analysis
Primary: functional_security minus functional_only in hidden joint pass rate. Also report hidden functional and security pass-rate differences. For each outcome, average model/seed differences within each of the 20 benchmark/task clusters; use 10000 task-cluster percentile bootstrap replicates and exact two-sided task sign flips. Apply Holm correction across these three endpoint tests. Sign-flip inference assumes symmetry under the null. Report estimates and intervals regardless of sign.

Descriptive analyses: all task/model outcomes; paired wins/losses/ties; each branch's four-state transitions from the common initial; functional regressions; function-preserving security repairs; actual feedback/input/output tokens; channel truncation; initial security-feedback opportunity. No outcome-dependent task filtering, optional stopping, new primary subgroup, prompt revision or hidden-driven feedback selection. The two-branch effect is kept separate from the earlier six-branch fixed-call study because feedback allocation differs.
